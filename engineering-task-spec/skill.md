# 设计与实施合同 — v2.0

## 职责
Worker 根据简报写一份设计；设计里包含一节“实施授权与合同”，用户确认后即是实施阶段交给 ReviewLoop 的合同。

## 设计的结构
1. **Options**：比较 2 到 3 条路线，优先最简单、最能复用的；每条被拒的路线写明原因。
2. **Assumptions**：简报没说破、Worker 默认成立的前提，用大白话写；没有就写 None。
3. **设计要点**：对共享身份、存储、迁移、公共接口、重试与幂等等，沿真实数据流核对：谁是唯一权威、谁可以写、创建/修改/失败/重试/重启各发生什么、已有消费者是否真的用到。复用已有扩展点，不另造第二份权威。
4. **实施授权与合同**（见下）。

## 实施授权与合同
- **目标**与**范围、禁止事项**。
- **约束**：全局规则（如数据骨架）原样列出。
- **验收标准**：每项写“声明 → 可能怎样失败 → 足够的证据”，规定不能发生什么，而不只是“加测试”。
- **阶段**（可选）：简单任务只设一个完成门槛；有独立依赖才分阶段，通常两三个。每阶段有稳定编号、目标、退出条件、证据、带入下一阶段的不变量。
- **验证命令**与**必需证据**。
- **授权**：分别写明修改代码、提交、推送、创建 PR、合并、破坏性操作、权限与凭据变更；没写视为未授权。
- **关口**：会停下来找用户的情况（如建取件令牌、用户验收、合并）。除此之外连续做完。

设计评审通过后，设计内容的指纹（含这一节）固定；实施前先核对指纹，合同原文交给评审，不改写。合同要写成自包含：只给链接不带操作约束不算。

## 证据的最低要求（按主张选，不堆清单）
- 集成：真实调用链和代表性既有消费者；界面接线要运行交互或端到端检查。
- 持久化/迁移：写入或迁移后重载或重启再检查，旧数据和关联仍在。
- 故障/重试/并发：故障要注入到所声称的阶段，断言目标阶段和副作用，不能被更早的保护拦下后误报通过。
- 导出/删除：回读导出内容；检查持久化删除及下游状态。
- 科研：已知答案、物理或数值不变量、容差、缺失与常量等边界；数量、单位、方法、显示映射分别验证。无参考时明说哪些主张未证实。

## 开工前的检查
工作区已有改动、实际基线、已有失败、检查入口、测试数据与权限。已验证的命令才写成事实，没验证的让 Worker 查明。若与冻结的前提实质冲突或必需证据拿不到，停止相关实施并精确报告。

## 完成时交付
合同版本、基线与提交、PR 或可检查的差异、逐条验收对应的证据、真实的评审结果、未验证项、用户的验收步骤。不以 Worker 自述代替独立评审。保护原始数据、现有编辑与无关行为，不为变绿而弱化验证。
