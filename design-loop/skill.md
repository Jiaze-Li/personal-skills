# 设计工作流

用户带着一个需求来找你时，按这份文件工作。它适用于任何需要先想清楚再动手的任务：新功能、架构改动、流程设计。只改一两行的小修不需要。

工作分三段。用户只需要出现在第一段，以及循环暂停的时候。

| 阶段 | 做什么 | 谁做 |
| --- | --- | --- |
| 一、谈清楚 | 找到真正的问题，写出 brief | 你和用户 |
| 二、定合同 | 写合同，开 PR，运行评审循环直到通过或暂停 | 你和脚本 |
| 三、实现 | 按通过的合同实现 | 新的 agent 会话 |

## 阶段一：谈清楚

用户说出来的通常是一个方案，不一定是问题。用户也可能不知道还有别的做法。你在这一段的任务是替他把问题找出来，把别的做法摆出来，而不是马上照做。

先读 `step-back.md`，然后按这个顺序做：

1. **复述问题。** 用一句话说出你理解的问题，不用用户提到的方案里的词。问他对不对。
2. **提问。** 列出你正在做的假设，然后只问那些“答案会改变设计”的问题，最多五个，一次问完。每个问题给出你的默认答案，用户可以直接说“按你的来”。必问的三个：谁用（有没有别人，要不要防恶意），失败一次的代价，什么明确不做。
3. **摆出别的做法。** 至少给出三种：用户说的做法、你能想到的最简单的做法、不做。再加上任何性质完全不同的路线。每种写一句代价。说出你推荐哪个，以及为什么。
4. **提出异议。** 如果你认为用户的方案不是最好的，直接说，并给出理由。用户不同意时按用户的来，把这个决定记进 brief。
5. **写 brief。** 照 `brief-template.md` 写到 `design/<任务名>/brief.md`。只写用户确认过的内容；你的推测放进「未确认的假设」，逐条问完后移走，直到那一节只剩“无”。
6. **让用户确认 brief。** 用户说可以，这一段才结束。

不要在这一段写合同或代码。

## 阶段二：定合同

1. 新建任务分支。写 `design/<任务名>/contract.md`：合同说明要做什么、怎么做、怎么验收。
   - 合同要短。brief 没要求的东西不写。
   - 一个文件，文件名不带版本号。历史由 git 记录，不要在合同里写修订记录。
   - 每个二级标题（`## `）对应一块独立的内容。评审按二级标题定位问题。
2. 提交 brief 和合同，推送，开 draft PR。
3. 在仓库根目录、PR 分支上，以后台命令运行循环：

   ```bash
   node ~/personal-skills/design-loop/design-loop.mjs <PR号> design/<任务名>
   ```

   脚本自己完成评审、分诊、修改、提交、推送和发 PR 评论。运行期间你不需要做任何事，不要轮询，不要查看进度。等它退出。
4. 按退出码处理：

   | 退出码 | 含义 | 你做什么 |
   | --- | --- | --- |
   | 0 | 合同通过 | 告诉用户合同在哪个提交通过，PR 链接是什么。停止 |
   | 2 | 已暂停，需要用户决定 | 见下面“暂停时” |
   | 1 | 运行出错 | 把错误信息原样告诉用户。同一个错误不要重试超过一次 |

### 暂停时

脚本已经在 PR 上发了一条评论，写明暂停原因、局外人视角和选项。

1. 把这条评论的内容转述给用户：原因、选项、推荐。不要自己选。
2. 用户决定后，把决定加日期写进 brief 的「已定决定」。如果决定改变了范围，同步修改合同。提交并推送。
3. 运行：

   ```bash
   node ~/personal-skills/design-loop/design-loop.mjs <PR号> design/<任务名> --resume
   ```

你不能做的事：不经用户决定就加 `--resume`；为了让循环继续而修改 brief；删除或编辑脚本发的评论；改 `MAX_ROUNDS` 之类的限制来绕过暂停。

## 阶段三：实现

合同通过后，用户会开一个新的会话说“执行 PR xx”。新会话要做的：

1. 读 PR 上最后一条设计循环评论，确认结论是 PASS，记下它对应的提交。
2. 确认 `design/<任务名>/` 下的两个文件在那个提交之后没有改动。有改动就停下来告诉用户，需要重新跑循环。
3. 按合同实现。发现合同做不到或有错时，停下来告诉用户，不要悄悄偏离合同。

## 任何时候都适用

遇到 `step-back.md` 里列的触发条件，就停下来按它做。这条规则优先于“把手头的事做完”。
