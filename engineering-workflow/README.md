# AI Engineering Workflow v2.0

## 一句话
每个任务都先出设计：简报（只授权出方案）→ 设计（含“实施授权与合同”一节）→ 用户确认 → 连续实施 → 评审 → 用户验收并决定合并。不再按风险分流，所有任务同一条路。

## 角色
- **用户**：定方向，确认前提和授权，验收，决定合并。
- **主控**（可选，ChatGPT 或 Claude 会话）：把想法收敛成简报。规范见 [`../engineering-lead/skill.md`](../engineering-lead/skill.md)。
- **Worker**（本地 Coding Agent）：写设计、合同和代码。格式见 [`../engineering-task-spec/skill.md`](../engineering-task-spec/skill.md)。
- **ReviewLoop**：独立评审设计和代码；PR 机器人评审 PR。工具用法见 ReviewLoop 的 Worker 合同。
- 没有单独的架构师、审查员角色：设计由 Worker 写、ReviewLoop 评审，不另开对话。

## 流程
1. **简报。** 要做成什么、不做什么、验收步骤、授权。授权一律是“只出方案”。开一个草稿 PR，描述顶部放简报要点，之后全程只用这一个 PR。
2. **设计。** Worker 以 ReviewLoop 的设计模式写设计：比较过的路线（含被拒原因）、没说破的前提、设计要点，以及“实施授权与合同”一节。评审通过后，在 PR 评论里贴不超过五行的大白话：做成什么、需要用户确认的前提、授权草案。
3. **确认。** 用户在 PR 上用自己的话确认前提和实施授权，例如“确认，做到代码审查通过”。授权只在用户确认后生效；Worker 起草的授权不自动生效。
4. **实施。** 先核对设计的指纹未变；把设计里的合同一节原文交给评审，分阶段登记；各阶段连续做，阶段通过不再询问用户。
5. **收尾。** 执行项目自己的收尾要求（写在项目说明里）；提交并推送；PR 描述更新为：做了什么、验收清单、已验证项、风险与偏离。
6. **PR 评审。** 机器人评审，有返工就修，直到就绪。
7. **验收与合并。** 用户按验收清单亲手走一遍；合并永远由用户决定。

## 只有这些情况才停下来找用户
- 缺只有用户才有的东西：产品取舍、密钥凭据、不可逆操作的确认。
- 评审要求人工介入。
- 合同里列出的关口。

做完一个阶段、一轮汇报、或“要用户做的：没有”，都不是停下来的理由。

## 授权
每个任务分别写明是否授权：修改代码、提交、推送、创建 PR、合并、破坏性操作、权限与凭据变更。没写的不得推定已授权。用户可一次授权完整操作链。

## 记录
- 提交首行是进度条目，要写清项目层面的变化，不写“更新”“wip”。
- 每轮结束记一句“下一步”。
- 进度、技术债等的具体存放位置由项目说明规定，不在这里另设。

## 交给另一个对话
优先给已有的 PR、Issue、正式合同和固定提交的引用，不让用户整理长聊天。需要提示词时，给一个可一次复制的完整代码块，写清去哪里、带什么、回来什么。每个新任务开始时记下本仓库的 commit，同一任务后续都按它读取规范。
