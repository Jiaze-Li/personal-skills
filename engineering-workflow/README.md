# AI Engineering Workflow v1.0.4 — 使用说明

## 结论
采用“一个主控 GPT 对话 + 一个 Coding Agent Worker + 必要时独立 Reviewer”。四份 Skill 分隔职责，不要求四个常驻 GPT 对话，也不新建一套执行系统。

四份规范保存在 personal-skills 的 main 分支，供 ChatGPT Project 按职责通过 GitHub 动态读取。文件存在不等于当前会话已经加载；实际任务的独立设计审查与试跑仍需执行，不能自称已验证。

## Actionable Handoff（可执行交接）

**用户可直接行动优先于技术流水账。** 面向用户的阶段回复先交代**当前结论/状态**（可以开发、待审查、须返工或已结束），接着给**唯一明确的下一步**；需要用户操作时写清操作顺序，不只说“准备好了文件/合同”。只有存在重大产品、科研、架构取舍或额外权限需求时，才在文末集中给问题、推荐和用户要回答什么；没有就不增加确认环节。实现明细、SHA 和证据可放在交接包内，不代替行动说明。

**切换另一个对话或 Worker 时**，优先一个可用的完整包或精确可访问引用，明确：
- **去哪里：** 继续当前 Worker / 新建独立 Reviewer 对话（写清选哪个）。
- **带什么：** 文件包名称及实际下载链接，或准确引用；需要时写“下载 → 新建对话 → 上传”，不让用户自行从多个报告拼材料。
- **发什么：** 已准备好的完整可复制 Prompt，不要求用户自行撰写。
- **回来什么：** 对方应返回的结论/文件，以及把结果交回哪里。

**如文件未实际生成或无法验证链接，不得假称可下载；**改给自包含文本或明确缺口。若冻结合同已经满足实施前提，就明确写“下一步可开始代码开发”，并提供已授权范围内的 Worker Prompt；仍有 Gate 阻塞则明确不可开发。正式 Worker Prompt 前可有一句用户操作提示，Prompt 本身仍保持一个完整代码块。

**用户手动交接以 1 次为目标，2 次通常可接受。** 不因此减少必要独立审查、绕过强制关卡或预先宣称自动委派成功；超过时说明具体阻塞和为何不能复用现有工具。四角色正文只作简短引用，本节是唯一详细的用户交接规范。

## ChatGPT Project Settings（复制到项目设置）

```text
当我提出软件工程相关需求（规划、架构、Coding Agent Prompt、PR 审查、实现评估、缺陷修复）时：
1. 使用已连接的 GitHub 读取 Jiaze-Li/personal-skills。每个新任务开始时从 main 取得完整 commit SHA 作为 policy_sha；同一任务后续规划、设计、Task Spec、独立 Reviewer 均从该 SHA 读取对应 Skill，不因 main 更新静默切换。旧任务缺少 SHA 时不得虚构，保留原冻结合同。
2. 默认由 engineering-lead/skill.md 统筹，按需读取 engineering-architect/skill.md 和 engineering-task-spec/skill.md；独立审查在另一个上下文按同一 policy_sha 读取 engineering-reviewer/skill.md。不要无条件加载全部 Skill；无法读取时明确说明，不假装遵循。
3. 简单任务走短流程；涉及共享权威、身份、持久化/迁移、重大科研计算或其他高风险变化时检查底层依赖并按分级独立审设计。DESIGN PASS、USER WAIVED、PENDING 必须区分。豁免须有我针对该合同明确的风险知情与继续实施授权，不代表 PASS，也不能绕过实质阻塞或强制关卡。
4. 任务合同自包含、可执行、可验收，明确修改、commit、push、PR、merge 和破坏性操作/权限各自授权范围，未明确授权的操作不得推定。
5. 完整审查相关范围后集中反馈、集中修复、完整复审。Reviewer 可在未知执行状态下只读审查，但下发可执行修复 Prompt 前必须核实原任务/loop 及最新可信状态、适用 PR 和 bot 的 HEAD/审查状态；HUMAN_REQUIRED 必须停止。
6. 连续两轮修复在同一共享设计或事务/权威边界引入新系统性阻塞时暂停局部补丁，先做只读根因审计。优先复用已安装 ReviewLoop Worker Policy 和 PR bot，不重复已充分覆盖的关卡，不将未经验证的证据写成 PASS。
7. 尽量减少我手动转译或切换角色。每次结论都告诉我当前状态、明确下一步和我需要执行的操作；跨角色交接提供最少附件或准确引用、具体上传步骤、完整可复制 Prompt 及结果回传方式，携带 policy_sha 与合同版本。重要产品、科研、架构和额外权限决定集中在文末由我确认。
8. 默认只读；未经明确授权，不修改仓库、提交、推送、合并 PR、改权限或破坏正式数据。新的方法规范不自动改写已冻结任务的合同；现行工具、仓库和安全强制要求仍须遵守。
```

## 跨角色接口规则

- **Gate 判定唯一归 Lead：** Tier 1 跳过独立设计审查；Tier 3 需要独立设计审查；Tier 2 只有修改共享权威、Schema/持久化、事务恢复或关键跨模块不变量才强制 Gate。**调用 Architect 不等于强制 Gate**；普通 Tier 2 兼容扩展可有设计依据且 Gate=N/A。Gate 必需时，只有对确切 `design_ref` 的 DESIGN PASS 或有效 USER WAIVED（且没有其他实质阻塞）才能编译实施任务。
- **输出格式由交付物决定：** 讨论/规划听 Lead，Architecture Contract 听 Architect；正式 Coding Agent Prompt 是一句用户操作提示加 Task Spec 的单代码块；独立审查听 Reviewer。均遵循上面的 Actionable Handoff，不改变权限、合同和 Gate 约束。
- **统一方法基线：** 新任务读 `main` 并固定完整 `policy_sha`；后续 Architect/Task Spec/Reviewer 读取相同 SHA。`policy_sha` 固定角色规范；`design_ref` 固定 Reviewer 批准的确切架构合同（Git commit+path 或经工具计算 SHA-256+原文），不得仅凭合同名称/版本推断批准范围。旧任务缺少记录则说明未知，不回填猜测的版本。当前工具/安全强制规则仍生效。
- **设计豁免：** `DESIGN PASS`、`USER WAIVED`、`PENDING`、`N/A` 分开；豁免只有经用户对相同不可变 `design_ref` 明确知情并授权继续才生效，不替代设计合理性，也不能绕过真实阻塞。
- **逐项操作授权：** 不因要交付 PR 就默认为已授权所有 commit/push/merge；Lead 收敛并由 Task Spec 写进 Worker 合同，未授权动作不得执行。
- **Reviewer 不能绕过 Worker Policy：** 在确认原任务/loop 状态、PR HEAD 和相应 bot 证据后才下发可执行修复 Prompt；`HUMAN_REQUIRED` 停止并报告；等待、预算及 PR bot 强制关卡不能靠新任务、新审查状态或改 AC 绕过。缺少状态仍可只读审查但不能下发可立即执行的修复。

### 风险分流与执行评测（输入及记录表见 [EVALS.md](EVALS.md)，待实际试跑）

| 场景 | 正确路径 |
|---|---|
| 局部 UI 按钮修改，既有合同稳定 | Lead → Task Spec → Worker；无额外设计 Gate；最终 prompt 单代码块 |
| SpinLab Sample 永久身份和跨模块关联调整 | Lead 判 Tier 3 → Architect Contract → DESIGN PASS 或有效 USER WAIVED → Task Spec → Worker；基础实施与消费者证据先于依赖功能 |
| PR REWORK 后 ReviewLoop 为 HUMAN_REQUIRED | Reviewer 报告阻塞，不能交给 Worker 绕过当前状态继续修复 |

## 文件与负责人
| 规范 | 使用位置 | 唯一主要职责 |
|---|---|---|
| engineering-lead/skill.md | 主控对话 A，日常入口 | 目标、依赖排序、阶段分流、项目状态和交接 |
| engineering-architect/skill.md | A 的按需架构阶段 | 共用权威、边界、不变量、状态/失败合同 |
| engineering-task-spec/skill.md | A 的任务编写阶段 | 单个自包含 Worker prompt、AC 与证据义务 |
| engineering-reviewer/skill.md | 独立对话 B 或有等效能力的独立审查者 | 设计/实施判定、完整 findings 和修复交接 |

Worker 复用现场既有 Worker Policy；没有新增第五份 Worker Skill。专业科学检查按相关任务触发，不设常驻科学审查角色。

## 为什么同一个 GPT 仍可做三件事
规划、架构与任务设计是兼容的连续工作，不需要为了名字不同而拆聊天。必须分开的，是自己的方案/实现与其“独立批准”。B 不必换模型，但必须有独立审查上下文和可检查输入；这不保证消除所有共同盲点。

A 按阶段读取对应规范，不要求所有规范一直塞进一个系统提示。已经进入聊天历史的内容不会因角色切换自动消失；对话过长时用项目记录和当前合同换新会话，而不是继续堆积。

## 名词：冻结合同与 PR

- **冻结合同（Frozen Contract）**：你确认后，任务目标、范围、全局验收标准、必要架构约束与验证义务固定下来。修 Bug 可以在原任务内继续，不能为了通过审查偷偷改标准。必要的实质变更由你批准并明确记录。
- **PR（Pull Request）**：GitHub 上请求把某个分支的修改合并入目标分支的记录。它包含代码差异、评论和审查状态；PR 创建不代表通过，也不代表已合并。

## 日常怎么做
### 普通任务
在 A 说需求。A 查相关仓库，读取 task-spec，给一个完整 prompt。将它一次复制给 Worker。Worker 按既有政策实施、验证、处理普通自动审查反馈，交 PR 和证据。独立代码审查已充分完成则不额外开 B 重做同样检查；若没有可靠独立审查，或你明确要求 GPT 检查 PR，则把完成包给 B。

只有合同明确要求真实使用/科研验收时，你才做对应操作。A 收到有效审查及必需外部验收结果后更新任务状态；merge 仍按你授权，不因 PASS 自动进行。

### 高风险或共享架构任务
A 根据 Tier 判定是否读取 Architect，并**单独**判定是否需要独立设计 Gate。Gate=N/A 时，形成必要的架构说明后可以直接交 Task Spec；Gate=REQUIRED 时形成含不可变 `design_ref` 的短架构合同及审查包，交 B 进行独立审核。**只有同一 `design_ref` 获 DESIGN PASS，或用户针对该内容明确知情豁免并授权继续（USER WAIVED），且没有其他实质阻塞，才可编译 Worker Prompt。** B 的 PASS 不等于实际基础完成。基础不一定单独开任务：小型变更可放在同一任务的先行阶段，但依赖功能必须等基础门槛通过。跨任务复用或独立迁移/发布时再拆任务。

设计已获批但基础尚未实现时，不得将基础标为可用。已存在并保持不变的获批设计不为每个后续功能重新过设计审查。

### 返工
普通实现缺陷：B 完成全范围审查后给一份集中修复 prompt，直接复制给原 Worker；不必绕回 A 重新措辞。重大产品/架构变化才回 A。自动审查已能驱动的普通修复由 Worker 处理，不让用户逐条转述。

## 与你当前 ReviewLoop 的关系
核查时读取的仓库 `Jiaze-Li/reviewloop/agent-policy/COMMON.md` 为 Worker Contract 8，blob `08b35705a2b8347dca287e82f221828d0293777c`。它规定本地 ReviewLoop 独立检查，push 后由 claude-review-bot 负责 PR 审查，并绑定 PR HEAD。这里核查的是仓库政策，未验证你本机当前安装版本或某个 PR 的 bot 状态。

因此新工作流不取代这些关卡，也不强制在其后再加一轮同范围 GPT Review。B 的主要新增价值是实施前设计审查，以及已有代码审查未覆盖的跨任务/产品/科研验收；用户明确要求的完整 PR 检查仍由 B 进行。已有审查充分与否必须看合同、提交和证据，而非只看一个 PASS 字样。

开工时在任务合同中明确：设计审查是否需要及由谁做、独立代码审查路径、外部验收是否需要。工具既有强制关卡仍按实际政策执行；没有受支持的桥接时，不能假称 GPT 的 PASS 自动写回 ReviewLoop 或 bot。

## 只保留两类项目材料
长期项目使用一份已有项目页/文档维护目标、重要决定/架构引用与状态、路线图、当前任务。每个任务一份冻结合同，后续交付/审查证据放在其关联 issue/PR 中，尽量复用现有存储。简单一次性任务只需任务合同。

这是信息分类，不要求每类单独文件。共享基线与任务版本都必须可定位；复制到 prompt 的约束有来源，不成为可独立修改的第二权威。更新 GitHub 文档需要相应授权，不能因为“统筹”便默认可写。

### 最小项目记录（按需）
项目/仓库与核查基线、任务 `policy_sha`（无历史记录则标未知）：
目标和非目标：
重要决定/架构引用：版本；设计状态；实际落地证据；尚未落地范围。
任务：ID；目标；依赖；完成条件；状态/证据。
当前下一步与必要权限：

### 每次交接包（由 AI 整理，不由用户整理）
任务/合同版本与固定的 `policy_sha`；仓库、分支、base/head（适用时）；精确合同/设计内容或可访问版本；Gate 状态、适用的不可变 `design_ref`、审查/豁免依据及操作授权；PR/差异与 AC 证据；审查范围及结论；返工场景还须附当前 loop/PR bot 状态与所审 HEAD 的可信证据；未决项；接收者现在要做的事。

发给 Worker 的 prompt 自包含必要要求；发给 Reviewer 的材料包含足够需求与上下文，但不将作者的自信或 PASS 主张当证据。无法访问引用时附内容，不能靠回忆补全。

```text
我会与你讨论需求，再把你提供的一个完整 prompt 交给 Coding Agent 执行。
请你负责选择何时读取 architect 或 task-spec，不让我手工切换每种角色。
你不得给自己签发独立验收；需要独立审查时，直接整理好交接包。
保持现有 ReviewLoop/PR bot，不新增重复关卡。默认只读，不提交或修改仓库。
项目仓库：<仓库>。当前目标：<目标>。
```

### 独立 Reviewer B（需要时新开，不用 A 改名冒充）
```text
通过已连接的 GitHub，按交接包中的 policy_sha（不是任意最新 main）读取 Jiaze-Li/personal-skills 的 engineering-reviewer/skill.md，并独立审查下面的交接包。旧任务无 SHA 时标明未知且不得倒改原验收合同。

我未授权你修改代码、数据、合同或合并 PR。
<粘贴 A 的设计审查包，或 Worker 的完成包与任务合同>
```

### Worker
不需要另写启动语。将 A 生成的完整任务代码块交给现有 Agent；实际执行政策继续按现场安装版。Worker 的完成包用于审查，不是自签完成证书。

日后回 A 通常只需说“审查结果和必要用户验收如下，请核对后更新进度并给下一任务”，不复制整段历史。仓库内容可读时直接给精确 PR/提交引用。

## 用 SpinLab 演示（说明流程，不断言当前代码状态）
目标：手机可创建 Sample。
A 先检查是否已有统一身份、唯一权威和相关消费者合同；若缺失，则设计 displayName/旧 sampleKey/永久身份的关系及必要兼容边界，由 B 审设计。
A 再给最小基础实施任务（或先行阶段）：证实创建与相关读取走同一身份，改名不会断关联，必要旧数据/重启场景成立。
在 Worker 实际基线包含已验证基础后，才让手机创建入口消费它。Notebook 等后续能力复用同一合同，不各自发明身份。
这不要求先建完所有未来数据库表、所有消费者功能或整个统一平台。

## 动态评测怎么做
无需增加常驻 Agent 或后台控制器。每次修改四份工程 Skill 或 Project Settings 后，使用固定 `policy_sha` 在**新的主控对话 A 和独立审查对话 B**运行 [EVALS.md](EVALS.md) 的案例：既测试正确阻塞，也测试符合条件时能顺利交接。每个案例保存实际原始输出、模型/环境、所用 SHA、期望与实测分流、阻塞/权限处理、PASS/FAIL 及证据链接；只读模拟测试不允许声称真的运行过 Worker 或 PR bot。

**发布门槛：** 正反向案例没有真实运行与证据，状态为 NOT RUN；出现 P1 的 FAIL 则修复并重跑对应案例和相关回归；其余问题记录后可作阶段性试用判断。模拟评测完成后，用一次真实 Tier 1 任务、一次共享基础任务和一次 PR REWORK 闭环记录实战证据。规范改动时重跑固定案例；真实任务结束时抽查是否遵守 Gate、授权、引用和证据义务，不要求每天人工检查。

## 版本一致性、权限与评测
新任务在首次正式规划时固定 personal-skills 的完整 Git commit SHA，后续所有角色以其为唯一方法规范基线。现有 ReviewLoop/PR bot 的强制政策、状态及仓库安全规则不被旧方法快照覆盖；发生实质冲突需报告。Task Spec 必须分别记录是否允许修改、commit、push、创建 PR、merge 等操作，未获授权的不执行。设计审查可由用户明确知情豁免并授权继续，但不能跳过重大未决设计或强制关卡。请按 [固定评测案例](EVALS.md) 记录正反向的实际结果，不要把文字场景直接当作执行 PASS。
